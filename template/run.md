# borrow-practice 실행 (AI 용 입구)

> 사용자가 「`.borrow-practice/run.md` 읽고 진행해줘」라고 하면 이 문서에서 시작한다. 사람용 설명은 [README.md](README.md) 에 있다.

borrow-practice 는 다른 저장소(`.env` 의 `BORROW_SOURCES`)를 분석해, **이 저장소에 더하면 좋을 규칙·스킬·테스트 원칙·검사 설정을 추천**한다. 추천 범위는 지침으로 옮길 수 있는 것이고, 구현 패턴은 근거·참고로만 쓴다([common.md 「추천 범위」](common.md#추천-범위)). AI 는 신호를 근거로 분석·제안하고, 적용 여부는 **AI 와 사용자가 함께 결정**해 기록한다.

분석 방식은 소스마다 `state.json` 이 정한다. 사용자가 고르지 않는다.

| 소스의 `state.json` 항목 | 분석 | 신호 파일 |
|---|---|---|
| 없음 (첫 분석) | **전체 비교** — 원본과 이 저장소의 지금 상태를 나란히 | `signals/<date>-snapshot-<key>.md` |
| 있음 | **변경분** — 마지막 분석 지점부터 원본 최신까지. 그 사이 PR·문서 포함 | `signals/<date>-diff-<key>.md` |
| 있지만 보는 브랜치가 바뀜, 또는 그 커밋이 지금 브랜치 이력에 없음 (강제 push 등) | 전체 비교로 돌아감 (신호 머리말에 사유) | `signals/<date>-snapshot-<key>.md` |

## 0. 시작 전에

1. `.borrow-practice/` 에 `scan.mjs`·`common.md` 가 없으면 도구가 설치되지 않은 것이다. 멈추고 사용자에게 저장소 루트에서 `npx borrow-practice@latest init` 으로 설치하라고 안내한다.
2. `.borrow-practice/.env` 가 없으면 멈추고, 사용자에게 [README.md 「설정」](README.md#설정)대로 만들어 달라고 한다. `.env` 를 대신 채우지 않는다 — 어떤 저장소를 볼지는 사용자가 정한다.
3. [common.md](common.md) 의 「시작 전에」와 「하드 게이트」를 읽는다. 거르기·보고서·결정·적용 확인은 common.md 를 따른다.
4. 사용자가 소스를 지정했으면(「web-app 만」) `--source <key>` 를 붙인다. 키는 저장소 이름의 소문자다.
5. 사용자가 분석이 아닌 일을 시켰으면 아래 「분석 말고」로 간다.

## 1. 신호 추출

```bash
node .borrow-practice/scan.mjs                  # 등록된 전체 소스
node .borrow-practice/scan.mjs --source <key>   # 한 소스만
```

- 출력된 파일 이름으로 소스마다 어떤 분석이 됐는지 확인한다(`snapshot` / `diff`). 한 번의 실행에서 소스마다 다를 수 있다.
- `signals/<date>-profile.md` 는 이 저장소 프로필이다. 두 분석 모두 「이미 있음」과 「빈자리」의 근거로 쓴다.

## 2. 변경이 없으면

- diff 신호가 **「새 변경 없음」**이면 그 소스는 보고서를 쓰지 않고 「마지막 분석(`state.json` 의 `analyzed_at`) 이후 바뀐 것이 없다」고 사용자에게 알린다.
- 모든 소스가 그렇다면 여기서 끝낸다. 상태 반영도 하지 않는다(지점이 같아 바꿀 것이 없다).

## 3. 후보 고르기

### 전체 비교 신호

후보가 많다. 한 번에 다 읽지 말고 **종류별로 우선순위를 정해** 읽는다. 무엇을 읽든 후보는 지침 형태로 올린다([common.md 「추천 범위」](common.md#추천-범위)).

1. **규칙** — 원본 규칙 문서의 절 제목을 이 저장소 프로필의 절 제목과 맞춰 본다. 제목이 달라도 같은 주제일 수 있으니 이 저장소 규칙 문서 내용을 grep 해 확인한다. 이 저장소에 없는 주제가 후보다.
2. **스킬** — 「원본에만 있음」을 먼저 본다. 「양쪽 같은 이름」은 내용을 비교해 원본이 더 나은 부분만 후보로 남긴다. 이름은 끝 이름에서 `-guide` 같은 꼬리를 떼고 맞추므로 `docs/start-task-guide.md` 와 `skills/start-task/` 는 같은 이름이다.
3. **검사 설정** — eslint 규칙·tsconfig 옵션·훅·CI 명령 중 원본에만 있는 것. 이 저장소에 켰을 때 고쳐야 할 곳이 몇 개인지가 비용이다.
4. **테스트 원칙** — 「테스트 기법」 신호에서 찾는다. 신호의 줄 수는 테스트 파일 안의 정규식 일치라 단서일 뿐이다. 「예」 칸으로 오탐(도메인 필드 이름 등)을 먼저 거르고, 숫자 차이가 애매해도 넘기지 않는다. 원본 CI 가 실제로 돌리는 테스트는 숫자와 상관없이 표본 몇 개를 열어, 이 저장소에 같은 종류의 테스트가 비어 있는 영역(도메인·실패 경로 등)이 있는지 본다. 후보는 「무엇을 테스트로 고정한다」 같은 원칙으로 올린다.
5. **의존성** — 위 1~4 의 후보가 요구하는 것만 보고, 그 후보의 「비용」 칸에 「설치 필요」로 적는다. 의존성만으로 후보를 만들지 않는다.

### 변경분 신호

1. **PR** — 구간 안 머지 커밋에서 뽑은 PR 번호·제목, gh 가 인증돼 있으면 본문까지 있다. 「왜 바꿨는지」가 가장 잘 드러나는 곳이라 먼저 읽고, 지침 후보가 될 PR 을 고른다. 버그 수정 PR 은 「이런 사고가 있어 이런 규칙」의 근거가 되기 쉽다. PR 없이 머지된 브랜치는 커밋 목록으로 본다.
2. **AI 설정·스킬, 도구·검사 설정** — 「이 저장소에 같은 이름 있음」으로 표시된 것은 원본에서 **이번에 바뀐 부분**만 후보로 본다.
3. **테스트·코드 기법** — 「이 저장소 일치 줄 수」가 0 이면 빈자리 후보지만, 0 이 아니어도 원본의 쓰임새가 다르면 후보가 될 수 있다.
4. **그 밖의 문서** — 설계·가이드·결정 기록 등. 원본이 무엇을 왜 정했는지의 근거로 읽는다.
5. **새 의존성** — 위 후보가 요구하는 것만 보고, 그 후보의 「비용」 칸에 적는다.

후보마다 [common.md 「원본 읽기」](common.md#원본-읽기)대로 원본을 직접 읽는다.

## 4. 거르기·보고서

[common.md](common.md) 의 「거르기」와 「보고서」를 따른다. 보고서는 실행 한 번에 하나, `reports/<date>.md` 다. `<date>` 는 이번 신호 파일 이름의 날짜(실행한 곳의 로컬 날짜)를 그대로 쓴다. 소스마다 분석 방식(전체 비교 / 변경분과 그 구간)을 머리말에 적는다.

- 변경은 있지만 쓸 만한 후보가 없으면, 후보 없이 「무엇을 봤고 왜 후보가 없는지」만 짧게 쓰고 사용자에게 알린다. 이 경우에도 상태는 반영한다 — 같은 구간을 다음에 다시 읽지 않게.

## 5. 분석 지점 반영

보고서를 쓴 뒤에만 실행한다. 이번에 본 원본 최신 커밋이 소스마다 다음 분석의 시작점이 된다.

```bash
node .borrow-practice/scan.mjs --commit-state
```

## 6. 결정·적용 확인

[common.md](common.md) 의 「결정」과 「적용 확인」을 따른다.

## 분석 말고

어느 경우든 먼저 [common.md](common.md) 의 「시작 전에」와 「하드 게이트」를 읽는다.

| 사용자가 원하는 것 | 하는 일 |
|---|---|
| 이 저장소 프로필만 보기 | `node .borrow-practice/scan.mjs profile` 뒤 `signals/<date>-profile.md` 에서 물은 부분을 요약한다. `.env` 가 없어도 된다 |
| 채택한 것이 잘 적용돼 있는지 확인만 | `decisions.md` 의 채택 항목을 [common.md 「적용 확인」](common.md#적용-확인)대로 하나씩 확인하고 「적용 확인」 칸을 채운다. 새 보고서는 쓰지 않는다 |
| 보류해 둔 것 다시 보기 | `decisions.md` 의 보류 항목마다 「다시 볼 조건」을 확인하고, 충족된 것만 [common.md 「결정」](common.md#결정-ai-와-사용자)대로 하나씩 다시 묻는다. AI 가 혼자 확인할 수 없는 조건이면 사용자에게 지금 다시 볼지 묻는다 |
| 중간에 끊긴 결정 이어 가기 | 사용자가 가리킨 보고서(없으면 `reports/` 의 가장 최근)를 열고 `decisions.md` 에 아직 없는 후보부터 하나씩 이어서 묻는다. 신호를 다시 뽑지 않는다 |
| 처음부터 다시 분석 | `node .borrow-practice/scan.mjs reset --plan`(한 소스만이면 `--source <key>`, 결정까지 지우라고 했으면 `--all`)으로 지울 것을 확인해 사용자에게 보여 주고(출력은 JSON 이다 — `lines` 를 목록으로 풀어 보여 준다), 확인받은 뒤 `--plan` 을 빼고 실행한다. `shared` 에 나온 파일은 커밋돼 있어 지운 것을 커밋하면 팀 전체에 영향이 간다는 점을 알린다. 「결정까지」라고 하지 않았으면 `--all` 을 쓰지 않는다 |

## 신호 추출기 공통 사항

- 이 저장소 쪽은 **HEAD 커밋**을 본다. 커밋하지 않았거나 `.gitignore` 로 뺀 파일(개인 `CLAUDE.md`·스킬 래퍼 등)은 프로필에 없다. 그런 파일이 있으면 직접 열어 보고 판단에 넣는다.
- **AI 설정 밖의 스킬·가이드 문서**는 `config.json` 의 `skillPaths`(이 저장소만)와, AI 설정 문서가 본문에서 가리키는 마크다운(양쪽 모두)으로 잡힌다. 비어 있는데 이 저장소에 스킬 래퍼(`.claude/skills/` 등)가 있으면, 래퍼가 가리키는 원본을 직접 열어 보고 사용자에게 `skillPaths` 설정을 제안한다.
- eslint 규칙은 설정 파일에 직접 적은 것만 뽑힌다. 공유 설정(extends·recommended)이 켠 규칙은 보이지 않으니, 「이 저장소에 없음」으로 판단하기 전에 실제 설정을 확인한다.
- 신호는 판정이 없는 재료다. 수치만 보고 결론 내지 않는다.

## 파일

| 경로 | 담는 것 |
|---|---|
| `signals/<date>-profile.md` | 이 저장소 프로필 |
| `signals/<date>-snapshot-<key>.md` | 전체 비교 신호 |
| `signals/<date>-diff-<key>.md` | 변경분 신호 |
| `reports/<date>.md` | 분석 보고서 — AI 가 쓴다 |
| `decisions.md` | 결정 기록 — AI 와 사용자가 함께 쓴다 |
| `state.json` | 소스별 마지막 분석 지점 — `--commit-state` 와 `reset` 으로만 바뀐다 |
| `signals/.pending.json` | 이번 분석에서 본 원본 최신 지점 — 분석이 쓰고, `--commit-state` 가 `state.json` 으로 옮긴 뒤 지운다. 직접 고치지 않는다 |
| `.cache/repos/<key>.git` | 원본 bare 사본 — 원본 읽기에 쓴다 |
