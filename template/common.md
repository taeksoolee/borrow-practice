# 공통 절차 — 거르기·보고서·결정·적용 확인

전체 비교·변경분 모두 이 문서를 따른다. [run.md](run.md) 에서 신호를 뽑고 후보를 읽은 뒤 여기로 온다.

## 시작 전에

- **이 저장소의 규칙 문서를 먼저 읽는다.** `AGENTS.md`·`CLAUDE.md`·`AI.md`·`.cursor/rules/` 등 프로필의 「규칙 문서」에 나온 파일과, 커밋되지 않은 개인 규칙 파일이 있으면 그것까지 읽는다. 이 절차와 저장소 규칙이 부딪히면 **저장소 규칙이 우선**한다 (커밋 형식·일감 규칙·의존성 규칙 등).
- `decisions.md` 가 있으면 읽는다. 이미 결정된 기법은 다시 후보로 올리지 않는다. 원본이 그 기법을 크게 바꿨을 때만 「재검토」로 올린다.

## 하드 게이트

1. **적용 여부는 혼자 정하지 않는다.** AI 는 분석과 제안까지 하고, 결정은 사용자와 함께 한다. 결정 전에는 코드를 고치지 않는다.
2. **결정이 나도 이 절차 안에서 적용하지 않는다.** 채택한 항목은 이 저장소의 평소 작업 흐름(브랜치·일감·PR)으로 따로 진행한다.
3. **일감(이슈)을 만들지 않는다.** 필요해 보이면 한 줄로 제안만 한다.
4. **의존성을 설치하지 않는다.** 새 라이브러리가 필요하면 「설치 필요」로 적는다.
5. **원본 저장소의 작업 트리를 쓰지 않는다.** 로컬에 원본 저장소가 따로 있어도, 다른 브랜치가 잡혀 있을 수 있다. `.cache/repos/` 의 bare 사본과 `origin/<branch>` ref 만 본다.

## 추천 범위

결정 대상은 **AI·팀 지침으로 옮길 수 있는 것**이다: 규칙, 스킬, 테스트 원칙, 검사 설정. 의존성은 단독 후보가 아니다 — 이들이 요구할 때 그 후보의 「비용」 칸에 「설치 필요: <패키지>」로 적는다.

- **지침인지 구현인지 가르는 기준:** 원본 코드를 가져오지 않고도 이 저장소에서 지키거나 검사할 수 있는 문장이면 지침이다. 특정 코드를 옮겨야만 지킬 수 있으면(「요청 취소는 `mergeAbortSignals` 로 한다」) 구현이다.
- **구현 패턴은 결정 대상이 아니다.** 맥락에 많이 기대 정기 점검에서 판단이 틀리기 쉽고, 채택해도 비용이 커 보류만 쌓이며, 「원본은 이 기능을 어떻게 했나」는 그 기능을 작업할 때 찾아볼 일이다.
- **구현은 근거로 쓴다.** 원본의 버그 수정·구현에서 「이런 사고가 있어 이런 규칙」을 뽑아낼 수 있으면 그 지침을 후보로 올리고, 구현은 근거·출처로 적는다. 뽑아낼 수 없으면 보고서 「참고」 절에 한 줄만 남긴다.
- 「참고」는 결정하지 않고 `decisions.md` 에도 기록하지 않는다. 그래서 처음부터 다시 분석하면 같은 참고가 다시 나올 수 있다 — 의도한 동작이다. 한 줄이라 부담이 작고, 기록하면 결정 대상이 아닌 것이 결정 기록에 쌓인다.

## 원본 읽기

신호 표의 수치만 보고 판단하지 않는다. 후보마다 **원본을 직접 읽는다.**

```bash
git -C .borrow-practice/.cache/repos/<key>.git show origin/<branch>:<path>   # 현재 파일
git -C .borrow-practice/.cache/repos/<key>.git show <sha>:<path>             # 특정 커밋의 파일
git -C .borrow-practice/.cache/repos/<key>.git show <sha>^:<path>            # 삭제된 파일 (지운 커밋의 부모)
git -C .borrow-practice/.cache/repos/<key>.git log --format='%h %an %ad %s' --date=short -5 origin/<branch> -- <path>   # 누가 언제 왜
```

- 경로를 셸 변수로 바꿔 쓸 때는 `"${REF}:${PATH}"` 처럼 중괄호로 감싼다. zsh 에서 `$REF:AGENTS.md` 는 `:A` 를 변수 수정자로 해석해 엉뚱한 경로가 된다.
- 테스트 기법은 **무엇을 단언하는지**까지 읽는다. 기법이 좋아도 잘못된 동작을 고정한 테스트일 수 있다.
- 규칙·스킬은 **어떤 사고나 문제 때문에 생겼는지** 커밋 메시지와 본문을 본다. 이 저장소에 같은 문제가 있는지가 빈자리 근거가 된다.
- 삭제된 스킬·규칙은 **왜 지웠는지** 커밋 메시지를 본다. 원본이 폐기한 것을 가져오지 않기 위해서다.

## 거르기

후보마다 아래 순서로 따지고, 걸리는 첫 단계에서 멈춘다.

| 단계 | 질문 | 걸리면 |
|---|---|---|
| 프레임워크 | 원본과 이 저장소의 프레임워크가 다른데(신호 머리말·프로필 참고), 그 기법이 원본 프레임워크 API 에 묶여 있는가. 원리가 프레임워크와 무관하고 원본의 구현(경로·프리셋·설정 이름)만 버리면 옮길 수 있으면 묶이지 않은 것으로 보고 다음 단계로 간다 | 제외 제안. 기법을 프레임워크 API 없이 다시 짜야 옮길 수 있으면 「원리만」으로 보류 제안 |
| 중복 | 이 저장소에 이미 같은 것이 있는가 (프로필 + 직접 grep + 규칙 문서 내용) | 제외 제안. 원본 쪽이 더 나은 점이 있으면 그 차이만 후보로 남긴다 |
| 빈자리 | 이 저장소에 **이것이 필요한 실제 자리**가 있는가 | 자리를 파일·함수·실제 사고로 특정하지 못하면 보류 제안 |
| 원본 상태 | 원본에서 실제로 돌고 있는가 (CI 가 그 테스트·검사를 실행하는지, 깨진 채 방치됐는지) | 돌지 않으면 「원본 미검증」으로 표시 |
| 비용 | 새 의존성, 설정 변경, 영향 파일 수, 기존 코드 수정량 (예: 규칙을 error 로 올리면 고칠 곳 수) | 보고서에 적는다 |

**이 저장소 쪽 근거도 직접 열어 확인한다.** 「중복」과 「빈자리」의 근거로 이 저장소의 코드·설정·라이브러리 동작을 들 때, grep 개수나 파일 이름만 보고 판단하지 않는다. 근거로 드는 자리를 열어 실제로 그 뜻인지 확인한 뒤 보고서에 쓴다. 원본만 읽고 이 저장소 쪽을 숫자로 끝내면 판단이 틀린다. 흔히 틀리는 모양은 이렇다.

| 숫자·이름만 보고 쓴 판단 | 열어 보니 |
|---|---|
| 어떤 패턴이 여러 곳에서 grep 되니 그만큼 빈자리가 있다 | 대부분 다른 용도였고 실제 자리는 한두 곳 |
| 규칙이 가리킬 출처(디자인 토큰·공통 유틸 등)가 없다 | 예상과 다른 이름·위치에 있었다 |
| 그 동작은 라이브러리가 처리한다 | 일부 경우만 처리했다 (라이브러리 코드를 열어 보고 알게 됨) |

- 「있다」「없다」를 쓰기 전에 무엇으로 확인했는지 보고서 메모에 남긴다 (파일 경로, 확인한 라이브러리 코드 위치).
- 확인하지 못했으면 「확인하지 않음」이라고 적는다. 추정을 사실처럼 쓰지 않는다.

## 보고서

파일은 실행 한 번에 하나, `reports/<date>.md` 다(같은 날 다시 돌리면 `-2` 처럼 번호를 붙인다). 판정 칸은 **AI 제안**이다. 결정은 다음 단계에서 한다.

```markdown
# borrow-practice 보고 — <date>

- 소스: <key> `<sha 8자리>` — 전체 비교 / 변경분 `<마지막 지점>..<sha>`
- 이 저장소: HEAD `<sha 8자리>`

## 후보

| # | AI 제안 | 종류 | 기법 | 출처 | 이 저장소의 적용 자리 | 빈자리 근거 | 비용 |
|---|---|---|---|---|---|---|---|
| 1 | 채택 | 테스트 원칙 | … | [파일](GitHub URL) — 작성자 | `src/…` | … | … |

## 후보별 메모
(후보마다 원본에서 읽은 핵심, 제안 이유, 반대 근거, 옮길 때 주의점)

## 적용 확인
(아래 「적용 확인」 결과)

## 제외 제안
(한 줄씩, 이유와 함께)

## 참고 (결정 대상 아님)
(지침으로 뽑아낼 수 없는 구현 패턴. 한 줄씩, 원본 링크와 함께. 결정·기록하지 않는다)
```

- 종류는 `규칙`·`스킬`·`테스트 원칙`·`검사 설정` 중 하나다. 필요한 의존성은 종류가 아니라 「비용」 칸에 「설치 필요: <패키지>」로 적는다. **테스트 원칙**은 이 저장소의 테스트 작성 규칙으로 적을 수 있는 것이다(예: 「실패 경로는 테스트로 고정한다」). 신호의 「테스트 기법」은 원칙을 찾는 재료이고, 특정 구현을 옮기는 것은 원칙이 아니다.
- 출처는 **GitHub URL** 로 적는다. 로컬 사본 경로는 다른 사람이 열 수 없다.
- 작성자를 적는다. 가져온 기법의 출처를 밝혀 원작자의 기여로 남기기 위해서다.
- 출처가 여러 파일이면 대표 파일 하나를 링크하고 「외 N개」를 붙인다. 나머지는 후보별 메모에 적는다. 작성자가 여럿이면 쉼표로 나열하고, 많으면 주된 작성자 뒤에 「외 N명」을 붙인다.

## 결정 (AI 와 사용자)

보고서의 후보를 **하나씩** 사용자에게 제시하고 함께 결정한다.

- 후보마다 AI 제안, 근거(빈자리 근거·원본 상태·비용), 반대 근거를 짧게 보여 준다. 여러 후보를 한꺼번에 묻지 않는다.
- 제시하기 전에 보고서에 적힌 **이 저장소 쪽 근거를 한 번 더 열어 확인**한다. 보고서를 다른 실행·세션이 썼다면 특히 그렇다. 틀린 근거를 찾으면 사용자에게 알리고 바로잡아 기록한다.
- 사용자가 제안과 다르게 정하면 그 이유를 묻고 함께 기록한다. 다음 분석에서 같은 판단을 되풀이하지 않기 위해서다.
- 결정 결과를 `decisions.md` 에 한 줄씩 더한다. 파일이 없으면 아래 머리말로 만든다.

```markdown
| 결정일 | 종류 | 기법 | 출처 | 결정 | 근거 | 적용 자리 | 진행 (일감·PR) | 적용 확인 |
|---|---|---|---|---|---|---|---|---|
| 2026-10-16 | 테스트 원칙 | 실패 경로를 테스트로 고정한다 | [useOrderForm.spec.ts](GitHub URL) — 작성자 | 채택 | … | `src/…` | | |
```

- 보고서의 「제외 제안」도 사용자 확인을 받아 `decisions.md` 에 「제외」로 기록한다. 하나씩 묻지 않고 목록을 보여 준 뒤 한꺼번에 확인받아도 된다. 기록하지 않으면 다음 실행에서 같은 것이 다시 후보로 올라온다.
- 결정은 **채택 / 보류 / 제외** 중 하나다. 보류는 다시 볼 조건(「모달 작업 때」, 「fast-check 도입 후」)을 근거 칸에 적는다.
- 결정하면서 추가로 조사했거나(이 저장소 코드 대조 등) 그 조사로 AI 제안과 결론이 바뀌었으면, 무엇을 확인했고 왜 바뀌었는지 근거 칸에 짧게 남긴다. 다음 실행이 같은 조사를 되풀이하지 않게 하기 위해서다.
- 채택한 항목은 저장소의 평소 작업 흐름으로 진행하고, 일감·PR 이 생기면 「진행」 칸을 채운다.

## 적용 확인

실행할 때마다 `decisions.md` 의 채택 항목 중 PR 이 머지된 것을 하나씩 확인하고, 결과를 「적용 확인」 칸과 보고서에 적는다.

- 이 저장소에 아직 남아 있는가 (적용 자리를 grep, 프로필의 해당 항목)
- CI 에서 실제로 실행되는가 (프로필의 「CI 실행 명령」·`.github/workflows/` 의 대상에 포함되는지)
- 원본에서 그 기법이 되돌려지거나 바뀌었는가 (diff 신호의 해당 경로 변경)

보류 항목은 근거 칸의 조건이 충족됐는지 함께 보고, 충족됐으면 결정으로 다시 올린다. 조건을 AI 가 혼자 확인할 수 없으면(「모달을 손볼 때」처럼 지난 작업에 걸린 조건 등) 추측하지 말고 사용자에게 「이 보류 항목, 지금 다시 볼까요?」라고 묻는다. 이 도구는 돌리는 시점에 판단하는 도구라, 보류 조건을 작업 중에 추적하지 않는다.

## 채택한 뒤

- PR 본문에 출처를 적는다: 「<저장소> <작성자>님 작업(GitHub URL)에서 가져옴」.
- 코드 주석에 출처를 남길 때는 커밋 해시나 파일 경로만 적지 않고 URL 로 적는다.
